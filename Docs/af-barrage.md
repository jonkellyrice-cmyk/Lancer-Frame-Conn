# Barrage

# AF — Barrage

## Status

**Native Barrage orchestration:** Not found.

**Native individual weapon attack flow:** Found.

**Frame Conn implementation status:** Requires Frame Conn-owned Barrage orchestration over native Lancer weapon attack execution.

## Purpose

This document records the native Foundry Lancer execution architecture relevant to the **Barrage** Full Action and defines the current plan for integrating Barrage execution into Frame Conn.

Barrage is unusual compared with actions such as Improvised Attack because the native Foundry Lancer system does not appear to expose a single `BarrageFlow`.

Instead, the system exposes a native attack flow for an individual weapon.

Therefore:

> **Native Lancer owns execution of an individual weapon attack.**
>
> **Frame Conn must own selection and sequencing of the weapons that constitute a Barrage.**

This is preferable to reimplementing weapon attacks inside Frame Conn.

Frame Conn should orchestrate existing native execution wherever possible.

—

# 1. Barrage Rules Structure

Barrage is a **Full Action**.

Unlike a simple single attack, Barrage operates through the mech’s weapon mounts.

A normal Barrage generally permits attacks using two weapon mounts.

Because mounts may contain multiple weapons, the number of individual weapon attacks generated by a Barrage may vary.

Conceptually:

- A mount may contain one weapon.
- Some mounts may contain two weapons.
- Two selected mounts may therefore produce multiple individual weapon attacks.
- A Superheavy weapon has special mount requirements and may occupy the capacity represented by more than one mount.

Consequently, Frame Conn cannot model Barrage simply as:

`Barrage -> attack twice`

The Barrage execution layer must understand the mech’s current loadout and mount topology.

—

# 2. Native Barrage Flow Search

Repository investigation did **not** reveal a dedicated native execution flow such as:

`BarrageFlow`

or an equivalent Barrage-specific native entry point.

Barrage does not appear to have the same sort of direct flow abstraction that some other actions possess.

Instead, the relevant native execution primitive is the system’s individual weapon attack flow.

—

# 3. Native Weapon Attack Entry Point

The native Lancer system exposes weapon attack execution through the weapon item.

The important entry point is:

`weapon.beginWeaponAttackFlow()`

This constructs and executes:

`WeaponAttackFlow`

Conceptually:

stock weapon roll button
→ resolve weapon `LancerItem`
→ `weapon.beginWeaponAttackFlow()`
→ `new WeaponAttackFlow(weapon)`
→ native weapon attack workflow

This is the native execution path Frame Conn should preserve.

Frame Conn should **not** recreate the weapon attack machinery unless a future requirement makes doing so unavoidable.

—

# 4. Native `WeaponAttackFlow`

`WeaponAttackFlow` operates on an individual weapon item.

Its native flow includes the following sequence:

`initAttackData`
→ `checkItemDestroyed`
→ `checkWeaponLoaded`
→ `checkItemLimited`
→ `checkItemCharged`
→ `setAttackTags`
→ `setAttackEffects`
→ `setAttackTargets`
→ `showAttackHUD`
→ `rollAttacks`
→ `applySelfHeat`
→ `updateItemAfterAction`
→ `printAttackCard`

This is extremely important for Frame Conn.

By entering the native flow through:

`weapon.beginWeaponAttackFlow()`

Frame Conn can retain native handling for such concerns as:

- weapon state
- destroyed weapons
- Loading
- Limited
- charge state
- weapon tags
- weapon effects
- targeting
- Accuracy
- Difficulty
- attack modifiers
- attack rolls
- self Heat
- post-action item mutation
- native chat output

The exact behavior should continue to belong to the native Lancer system whenever possible.

—

# 5. Native Mount Data

The native mech actor already contains weapon mount information.

The relevant structure is associated with:

`actor.system.loadout.weapon_mounts`

Weapon mounts contain slot information.

Conceptually:

Mech Actor
→ `system`
→ `loadout`
→ `weapon_mounts`
→ mount
→ slots
→ weapon references

Therefore Frame Conn should not need to invent a parallel representation of the mech’s equipped weapons.

The authoritative mount/loadout information should be read from the actor associated with the Frame Conn instance.

—

# 6. Architectural Boundary

The intended responsibility boundary is:

**FRAME CONN owns:**

- Barrage action selection
- Barrage mount selection
- Barrage legality presentation
- Barrage sequencing
- mapping selected mounts to weapons
- execution progression

**NATIVE LANCER SYSTEM owns:**

- individual weapon attack execution
- weapon attack targeting
- Accuracy / Difficulty
- attack modifiers
- attack rolls
- weapon state validation
- weapon resource mutation
- self Heat
- native attack chat output

In short:

Frame Conn asks:

> What attacks constitute this Barrage?

Native Lancer answers:

> Execute this weapon attack.

—

# 7. Proposed Initial Frame Conn Barrage Flow

The first implementation should use Frame Conn as a native-flow sequencer.

Proposed flow:

Player commits Barrage
→ Barrage appears in committed plan
→ Player presses execution / d20 control
→ Frame Conn opens Barrage weapon/mount selector
→ Frame Conn reads `actor.system.loadout.weapon_mounts`
→ Player chooses legal Barrage mount combination
→ Frame Conn expands selected mounts into weapon items
→ Weapon attack 1
→ `weapon.beginWeaponAttackFlow()`
→ native targeting / attack HUD
→ native attack execution
→ Weapon attack 2
→ `weapon.beginWeaponAttackFlow()`
→ native attack execution
→ additional weapon attacks if selected mount topology requires them
→ Barrage execution completes
→ committed Barrage marked executed

—

# 8. Multiple Targets

Barrage must not assume that every weapon attacks the same target.

The player may need to assign different attacks to different valid targets.

Therefore the initial execution architecture should allow each native weapon attack to perform its own target selection.

Conceptually:

Barrage
→ Weapon A
→ select target
→ attack
→ Weapon B
→ select target
→ attack

rather than:

Barrage
→ select one target
→ all weapons attack that target

Frame Conn may later provide a more efficient multi-target Barrage interface, but the underlying architecture must preserve the ability to attack different targets.

—

# 9. Barrage Mount Selector

Frame Conn will require a Barrage-specific selection surface.

The selector should be driven by authoritative actor loadout data rather than by a duplicate Frame Conn weapon registry.

Conceptually:

BARRAGE

Available mounts:

[ Mount A ]
  Weapon A

[ Mount B ]
  Weapon B
  Auxiliary Weapon C

[ Mount C ]
  Weapon D

Select legal Barrage configuration.

[ Execute Barrage ]

The exact UI should be designed only after the native mount topology has been fully documented.

—

# 10. Superheavy Weapons

Superheavy weapons require additional investigation.

A Superheavy Barrage cannot safely be implemented until we understand exactly how the native Lancer system represents the relationship between:

- the Superheavy weapon
- its mount
- the additional mount capacity required by the weapon
- the actor loadout
- weapon slots
- mount occupancy

We should **not** infer this representation from tabletop rules alone.

The zipped native repository should remain authoritative for how Foundry represents the loadout.

—

# 11. Main/Aux and Aux/Aux Mounts

Mounts containing multiple weapons also require explicit tracing.

We need to determine exactly how native loadout data represents:

- Main
- Main/Aux
- Aux/Aux
- Heavy
- Integrated
- Superheavy-related occupancy

Of particular importance:

`mount.slots`

We need to establish whether:

- each weapon has a distinct slot
- empty slots are represented explicitly
- slot ordering has semantic meaning
- auxiliary attacks are represented specially
- weapons are stored directly or by reference
- a Superheavy appears in multiple mount structures
- duplicated references can occur

Frame Conn’s Barrage selector must use the native representation rather than assuming the tabletop structure maps directly onto the document model.

# 13. Important Implementation Rule

Do not create a Frame Conn replacement for `WeaponAttackFlow` merely because Barrage itself lacks a native orchestration flow.

The preferred architecture is composition:

`FrameConnBarrageExecution`
→ native `WeaponAttackFlow`
→ native `WeaponAttackFlow`
→ native `WeaponAttackFlow`
→ ...

Frame Conn should add only the orchestration layer that is missing.

—

# 14. Future Automated Barrage Architecture

The first implementation should preserve the native attack HUD.

Eventually Frame Conn is intended to become more automated.

The desired later architecture is:

Committed Barrage
→ press d20
→ Frame Conn enters target-selection mode
→ player selects target(s)
→ Frame Conn determines relevant attack modifiers
→ Frame Conn determines Accuracy
→ Frame Conn determines Difficulty
→ Frame Conn determines flat modifiers
→ attack automatically rolled
→ hit/miss automatically determined
→ damage automatically rolled
→ damage automatically applied
→ statuses / conditions automatically applied or removed
→ weapon resources automatically updated
→ next Barrage weapon attack
→ Barrage completes

However, this should be built incrementally.

The native `WeaponAttackFlow` provides a functioning intermediate execution path while Frame Conn develops the additional automation required for the final player-facing experience.

—

# 15. Integration With Committed Plan

Barrage should ultimately follow the same committed-action execution model as other executable actions.

Conceptually:

Committed Plan

`BARRAGE                                      [d20]`
`Full Action`

Pressing the execution control should begin the Barrage orchestration process.

The committed action should not be considered fully executed merely because the first weapon attack has begun.

Completion should occur only after the Barrage execution sequence has finished or has been explicitly cancelled/terminated according to whatever execution-state model Frame Conn ultimately adopts.

—

# 16. Failure and Cancellation Considerations

Because Barrage consists of multiple native weapon flows, Frame Conn will eventually need to define behavior for interrupted execution.

Examples include:

- player cancels target selection
- weapon cannot fire
- weapon is destroyed
- Loading requirement prevents attack
- Limited resource unavailable
- weapon charge requirement fails
- native attack flow aborts
- actor state changes during Barrage
- player closes the attack dialog

The orchestration layer should distinguish between:

- Barrage started
- Barrage partially executed
- Barrage completed
- Barrage cancelled
- Barrage failed

This becomes particularly important because some weapon attacks may already have mutated authoritative Foundry documents before a later attack in the Barrage is cancelled.

Frame Conn should not attempt to silently roll those mutations back unless a reliable native transaction mechanism is discovered.

—

# 17. Current Working Conclusion

The Barrage research currently supports the following architecture:

**No dedicated native `BarrageFlow` found.**

**Native weapon attack execution exists.**

Native entry point:

`weapon.beginWeaponAttackFlow()`

Native execution object:

`WeaponAttackFlow`

Native mount data:

`actor.system.loadout.weapon_mounts`

Therefore Frame Conn must implement:

- Barrage selection
- mount interpretation
- legal weapon grouping
- attack sequencing
- Barrage execution state

Frame Conn should delegate each individual weapon attack to:

`WeaponAttackFlow`

This keeps Frame Conn aligned with its intended role:

> Frame Conn is an alternate player-facing command and presentation layer over the native Lancer system, not a replacement Lancer rules engine.

—
